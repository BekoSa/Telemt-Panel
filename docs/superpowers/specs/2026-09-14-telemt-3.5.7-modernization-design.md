# Telemt 3.5.7 Modernization Design

## Context

Telemt-Panel was last updated on 2026-04-04 and was built against the Telemt Control API available at that time. Telemt is now at 3.5.7 and its API, runtime controls, configuration model, and operational endpoints have expanded substantially.

The panel should be modernized incrementally instead of rewritten in one change. The existing server-side proxy, authentication model, CSRF protection, audit logging, and current UI remain useful foundations.

## Goals

1. Restore a modern, reproducible, testable runtime foundation.
2. Make the panel explicitly compatible with Telemt 3.5.7 while degrading clearly against older Telemt releases.
3. Expose current Telemt user, runtime-edge, WEB runtime, configuration, and reload capabilities.
4. Reduce deployment and operational surprises before performing a larger frontend build-system migration.
5. Preserve the current authentication boundary: Telemt credentials stay server-side and are never exposed to the browser.

## Non-goals for the first implementation phase

- No full frontend rewrite.
- No Express 5 migration in the foundation phase.
- No multi-node session-store redesign in the foundation phase.
- No replacement of the existing visual design.
- No direct browser access to the Telemt API.

## Current risks and known stale behavior

- Docker uses Node 20 while `package.json` permits Node 18; both should be retired from the supported runtime target.
- There is no committed lockfile, so production dependency resolution is not reproducible.
- Docker healthcheck calls `/auth/me`; an unauthenticated healthy process returns 401 there, so a healthy container can be marked unhealthy.
- The UI contains an April-era workaround saying `rotate-secret` is unavailable; Telemt 3.5.7 implements it.
- The panel does not expose newer Telemt endpoints such as readiness, TLS fingerprints, active IPs, enable/disable/reset-quota, config/reload, and WEB runtime lifecycle/session controls.
- The current frontend is a single large HTML file with browser-side Babel and CDN dependencies.
- GeoIP requests use plain HTTP to a third party.

## Architecture

### Foundation

Keep Express 4 for the first phase. Raise the runtime target to Node 24 LTS, add a lockfile, use `npm ci` in Docker/CI, add an unauthenticated panel liveness endpoint at `/healthz`, and add Node's built-in test runner as the initial test harness. Separate app construction from process startup enough to test server behavior without binding a production listener.

### Telemt compatibility layer

Continue to proxy Telemt under `/api/v1/*`, but add a small capability/bootstrap layer based on stable endpoints such as `/v1/health` and `/v1/system/info`. The browser should distinguish `unsupported`, `disabled`, `read_only`, and transient upstream failures instead of treating all failures as generic errors.

### User operations

Remove the obsolete rotate-secret warning path. Add enable, disable, and reset-quota actions with confirmation for destructive or disruptive operations. Preserve `If-Match` support where Telemt revisions are relevant.

### Runtime and WEB controls

Add current runtime-edge visibility, including TLS fingerprints. Add a dedicated WEB Runtime area for status, sessions, session detail/close, and lifecycle pause/drain/resume. Operator actions must have explicit confirmation and visible operation state.

### Config and reload

Add config read/edit through Telemt's current `GET/PATCH /v1/config` contract and reload through `/v1/system/reload`. Preserve optimistic concurrency with revision/`If-Match`, surface conflicts distinctly, and do not expose non-editable access data in the config editor.

### Frontend modernization

After API compatibility is covered by tests, move the browser application out of the monolithic runtime-Babel HTML file into a normal build pipeline. Remove browser JSX compilation and reduce third-party CDN runtime dependencies. Tighten CSP at that time rather than mixing it with API compatibility changes.

## Error handling

- Panel liveness (`/healthz`) reports only panel-process health; it must not require login and must not depend on Telemt availability.
- Telemt readiness is displayed separately from panel liveness.
- Upstream timeouts remain 504 and connection/proxy failures remain 502.
- Telemt `read_only` and capability-disabled responses are surfaced as explicit UI states.
- Revision conflicts remain distinct from generic validation errors.

## Testing strategy

Use Node's built-in `node:test` initially to avoid adding a large testing dependency. Foundation tests cover configuration validation, liveness behavior, and proxy behavior with a local mock upstream. CI runs syntax/tests before Docker build. Later Telemt feature plans add contract fixtures for relevant 3.5.7 response shapes.

## Delivery sequence

1. Foundation modernization: Node 24, lockfile, `npm ci`, healthcheck, test harness, startup separation, CI verification.
2. Telemt 3.5.7 compatibility and user actions.
3. Runtime-edge and WEB Runtime controls.
4. Config/reload management.
5. Frontend build-system/CSP/GeoIP modernization.

Each phase must remain deployable and independently reviewable.
